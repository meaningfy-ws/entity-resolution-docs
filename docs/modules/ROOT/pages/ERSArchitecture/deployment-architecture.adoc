= Deployment Architecture

This section describes the *reference deployment architecture* for ERSys and its companion components. It defines how the system is intended to be deployed and operated in a container-based environment for development, integration, and early operational use. The deployment described here is normative in terms of architectural boundaries, interface exposure, and responsibility allocation, but it is not prescriptive with respect to infrastructure scale, hosting provider, or cloud platform.

The primary purpose of this section is to make explicit:

* how the main system components are deployed and isolated at runtime,
* which interfaces are externally exposed versus internally consumed,
* where (authoritative) data is persisted,
* and which infrastructure services are assumed by the reference setup.

This section intentionally does not specify a production-grade cloud-native deployment, orchestration platform, or operational hardening profile. Concerns such as Kubernetes-based deployments, horizontal auto-scaling strategies, multi-region redundancy, managed cloud services, infrastructure-as-code pipelines, and platform-specific security controls are considered out of scope for this architecture document. Future deployment variants, including cloud-native or managed-service configurations, are expected to evolve as the system matures and may be addressed in dedicated deployment, operations, or cloud architecture documents, without altering the core architectural responsibilities, interfaces, or governance model defined here.

== Runtime topology and container grouping

In the reference deployment, every software element runs as a separate container on a container orchestration platform. The containers form three independently installable components, the Link Curation UI, the Entity Resolution Service (ERS) and the Entity Resolution Engine (ERE), plus a set of shared infrastructure services that are provisioned once for the whole system. This grouping reflects the authority boundaries established earlier:

* ERE is authoritative for clustering and canonical identity (`cluster_id`).
* ERS is authoritative for intake records, projection of clustering outcomes, user action trace, and delta exposure tracking.
* The Link Curation application is a consumer of projection state and a producer of structured recommendations.

=== Link Curation UI

The Link Curation UI is a single container. It serves the web application used by curators and acts as a reverse proxy that forwards every API call from the browser to the Curation API of the ERS.

The UI holds no data and uses no shared infrastructure: it does not access the message queue, the document store or any volume. All state-changing operations are executed through the Curation REST API. User authentication is handled by the Curation API; no external identity provider is required.

The Link Curation UI is the only component exposed to end users.

=== ERS

The ERS is built from a single image and runs as two containers:

* the *ERS API*, which exposes the ERS REST API to internal client systems such as the TED-SWS pipeline;
* the *Curation API*, which exposes the Curation REST API to the Link Curation UI only.

At runtime, ERS performs the following bounded responsibilities:

* Persist immutable EntityMention records identified by the correlation triad.
* Publish asynchronous resolution requests to ERE via the message queue.
* Integrate EntityMentionResolutionResponse messages idempotently.
* Replace the current Decision projection per mention.
* Expose the latest recorded `cluster_id` via REST.

Both containers use the document store for intake and projection records, the message queue for the exchange with ERE, and read their configuration from the shared configuration volume. Neither is exposed outside the internal network. Both can run as several replicas: the message infrastructure broadcasts every ERE outcome to all replicas, so each one is notified regardless of which replica submitted the request.

=== ERE

The ERE is a single container with no network interface and no inbound port. It consumes resolution requests from the message queue and publishes responses back to it; it never calls, and is never called by, the ERS or any other component directly.

The ERE keeps its clustering state in an embedded database stored on its own persistent data volume, together with the temporary files the engine spills to disk under memory pressure and its trained matching model. It reads its configuration from the shared configuration volume. Because the embedded database supports only one writer, the ERE must run as a single instance.

Alternative storage mechanisms may be used provided that the asynchronous message contract remains unchanged.

=== Shared infrastructure

The shared infrastructure is provisioned once and used by several components:

* The *message queue* carries resolution requests from ERS to ERE and responses back, and broadcasts ERE outcomes across ERS replicas. It is infrastructure, not authority. Requests the ERE has not yet taken wait in the queue, so the queue must have enough memory for the largest expected backlog.
* The *document store* holds EntityMention and Decision projection data for the ERS. It does not redefine clustering semantics and does not constitute an independent canonical registry.
* The *shared configuration volume* is mounted read-only by the ERS and ERE containers and holds their configuration files.
* The *ERE data volume* is mounted read-write by the ERE alone. It must be persistent and writable.

== Infrastructure roles and concrete technologies

The reference deployment maps abstract infrastructure roles to concrete technologies in order to provide a runnable baseline: Docker Engine as container runtime, docker-compose for service wiring, Nginx for web serving and reverse proxying in the Link Curation UI, Redis (6.2 or newer) for asynchronous messaging and notifications, FerretDB as the ERS document store, DuckDB as the embedded ERE store, and Docker volumes for persistent file storage. An operational deployment may use a managed container platform, a managed MongoDB-compatible document store (for example Amazon DocumentDB) and shared file system volumes in their place.

The concrete requirements for deploying these components are listed in xref:Installation/deployment-requirements.adoc[Deployment Requirements].

These mappings are illustrative rather than mandatory. Equivalent technologies may replace them provided that exposed interfaces remain unchanged, authority boundaries remain intact, asynchronous integration semantics are preserved, and projection replacement behaviour is unaffected.

== Network segmentation and trust zones

The deployment makes network segmentation explicit. Only the Link Curation UI is reachable by end users. The ERS API is reachable by internal client systems, and the Curation API only by the Link Curation UI; neither is exposed to the public network. The message queue, the document store and the volumes are reachable only by the components that use them.

ERE has no externally exposed control surface. All clustering communication occurs through asynchronous messaging.

This segmentation enforces a clean trust model at runtime. Clients interact with projection. Engines perform clustering. Infrastructure mediates transport without altering authority.

== Deployment variability and evolution

The deployment architecture described in this section is intended as a *reference baseline*. It supports reproducibility, clear responsibility boundaries, and traceable behaviour across interfaces. As operational requirements evolve, this deployment may be complemented by additional profiles, such as multi-node deployments, high-availability configurations, or cloud-native orchestrations using managed services.

In particular, the deployment of the Entity Resolution Engine is expected to vary across implementations. ERSys does not impose constraints on the internal deployment model of ERE components beyond adherence to the defined asynchronous interface and message semantics.

Such evolution must preserve the architectural invariants defined in earlier sections:

* `cluster_id` remains the canonical identifier produced by ERE;
* ERS remains projection-centric and exposure-disciplined;
* EntityMention remains immutable and triad-identified;
* asynchronous messaging remains the sole integration boundary.

Infrastructure may evolve. Authority boundaries may not.
