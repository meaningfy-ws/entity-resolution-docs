[#adr-c2n]
= ADR-C2N — ERS–ERE Message Types and Delivery Semantics

[NOTE]
====
Status: Accepted (revised 2026-09-30 to match ERSys 1.1.0)
====

== Context and Problem Statement

ERS and ERE interact in a distributed environment where message delivery may be delayed, duplicated, reordered, or partially fail.

Clustering outcomes are authoritative in ERE, while ERS is responsible for forwarding requests, correlating responses, and recording the latest placement.

The interaction model must therefore:

* Tolerate asynchronous variability without relying on strict ordering.
* Avoid hidden coupling to timing or delivery guarantees.
* Support user recommendations and exclusions using a uniform contract.

Explicit delivery and message-structure rules are required so that both components behave deterministically under retries, concurrency, and late responses.

== Decision

. *Communication Model*
.. ERS–ERE interaction is asynchronous.
.. The concrete transport technology is abstracted at this level.
.. The transport gives no delivery guarantee: a message can be lost if a component stops or the broker fails, and there is no acknowledgement or dead-letter mechanism.
.. Duplicate messages must nevertheless be tolerated.
.. Message ordering is not guaranteed and must not be relied upon.
.. All consumers must be idempotent.
.. A lost request or response is recovered through the time-budget path of xref:AnnexeC-ADRs/adra2.adoc#adr-a2n[ADR-A2N] (a provisional identifier) and through re-submission or later ERE outcomes for the same mention.
.. Message loss is an accepted risk.
. *Correlation*
.. Resolution requests and resolution responses are correlated using the mention identifier tuple (source_id, request_id, entity_type).
.. This tuple uniquely identifies the resolution context.
.. Error responses from ERE carry only the `ere_request_id` of the failed request (or `unknown` when the request could not be parsed), not the mention identifier tuple.
ERS logs them and does not change any Cluster Assignment; a caller still waiting falls back through the time-budget path.
.. No additional implicit correlation mechanism shall be assumed.
. *Unified Resolution Request Types*
.. All interactions from ERS to ERE use a unified resolution envelope.
.. Each message contains the following fields:
... entity_mention (including the mention identifiers)
... ere_request_id
... timestamp
... proposed_cluster_ids (optional list of cluster_id values)
... excluded_cluster_ids (optional list of cluster_id values)
.. The envelope carries no action type; the intent follows from which optional lists are filled:
... plain resolution (neither list is filled),
... recommendation (proposed_cluster_ids is filled),
... exclusion (excluded_cluster_ids is filled).
.. User actions are transmitted using the same message structure as initial resolution.
.. There is no separate reclustering message type: outcomes the ERE initiates itself (for example after a cluster rebuild) arrive as ordinary unsolicited resolution responses on the response channel, with an `ere_request_id` carrying the `ereNotification:` prefix defined in the xref:ERS-ERE-Contract/interface.adoc[ERS–ERE contract].
. *Response Handling*
.. Responses from ERE contain the clustering outcome for the given mention context.
.. ERS shall process responses idempotently.
.. ERS shall persist the latest cluster assignment returned by ERE.
.. ERS shall overwrite prior projections for the same mention when a new outcome is received.
.. Late, duplicate, or out-of-order responses are treated as normal behaviour.
.. The latest processed ERE outcome becomes the authoritative projection in ERS. If multiple responses are received for the same mention, the response with the most recent clustering state according to ERE semantics shall prevail.
.. ERS shall not reject a valid ERE response solely due to lateness relative to a client-facing synchronous request.
. *Error Handling*
.. Engine errors, timeouts, and partial failures are absorbed within the asynchronous boundary.
.. Such errors may influence synchronous API behaviour under the timeout model, but they shall not corrupt existing cluster assignments or projections.
.. No response from ERE shall invalidate previously confirmed cluster identifiers unless replaced by a new clustering outcome.

== Scope and Applicability

This decision applies to all ERS–ERE message exchanges related to resolution, recommendation-based resolution, exclusions, and reclustering.

It governs message structure, delivery assumptions, correlation semantics, idempotency, and projection update rules.

Broker configuration, infrastructure tuning, and low-level transport guarantees are out of scope.

== Considered Options

* Synchronous communication between ERS and ERE.
* Asynchronous exactly-once delivery guarantees with strict ordering assumptions.
* Asynchronous delivery without delivery guarantees, with idempotent consumers and recovery through the time-budget path. _(Selected)_

== Rationale

Asynchronous delivery without acknowledgement or dead-letter infrastructure keeps the messaging layer simple; the provisional identifier path and later ERE outcomes bound the effect of a lost message.

A unified message envelope simplifies reasoning about user recommendations, exclusions and initial resolution, since all are treated as resolution requests with optional cluster lists.

Idempotent processing and correlation by mention identifier ensure deterministic behaviour under retries and concurrency.

Treating late responses as normal behaviour prevents hidden timing dependencies and keeps clustering authority entirely in ERE.

== Consequences

* Both ERS and ERE must implement idempotent message handling.
* The system must tolerate duplicate and out-of-order responses without divergence.
* User recommendations and exclusions follow the same processing pipeline as initial resolution.
* A lost message leaves the mention on its provisional or previous Cluster Assignment until a re-submission or a later ERE outcome updates it.
* Messaging infrastructure may evolve without affecting clustering semantics, provided delivery assumptions remain consistent.
* Changing delivery guarantees (for example to exactly-once semantics) would require a new architectural decision.
