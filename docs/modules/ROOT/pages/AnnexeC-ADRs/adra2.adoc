[#adr-a2n]
= ADR-A2N — Provisional Identifier and Timeout Budget Model

[NOTE]
====
Status: Accepted (revised 2026-09-30 to match ERSys 1.1.0)
====

== Context and Problem Statement

Client systems require a canonical identifier for each accepted resolution request in order to maintain processing continuity and stable downstream references.

Resolution computation is asynchronous and subject to variable latency depending on data characteristics, engine load, and infrastructure conditions. A purely blocking model that returns an error on engine delay creates operational fragility and shifts timing uncertainty to clients.

At the same time, the system must enforce bounded client-facing response times and avoid indefinite blocking.

The architecture must therefore reconcile two constraints:

* Clients require a canonical identifier within a bounded time.
* The authoritative clustering outcome is produced by the ERE and may not be available within that time.

== Decision

Each resolution request is bounded by a time budget:

. For a single-mention request, one budget serves both as the ERS–ERE execution window and as the bound on the ERS response.
. For a bulk request, each mention is resolved concurrently within that execution window, and the whole request is bounded by a separate bulk budget.

Client-facing resolution APIs are synchronous and blocking within these budgets. The client's own timeout must be longer than the budget of the request it sends.

For each valid resolution request:

. ERS forwards the resolution request to the ERE.
. ERS waits for an ERE response within the ERS–ERE execution window.

If the ERE returns a clustering outcome within the execution window:

* ERS returns the cluster identifier provided by ERE as the canonical identifier.
* ERS persists the placement as the latest known assignment.

If the ERE does not return a clustering outcome within the execution window:

* ERS issues a provisional singleton cluster identifier.
* The provisional identifier is returned to the client as the canonical identifier for that request.

ERS sends no further message to the ERE: the ERE keeps processing the original request.
Because the provisional identifier is derived with the same rule the ERE uses for a new singleton cluster (see xref:AnnexeC-ADRs/adra1.adoc#adr-a1n[ADR-A1N]), the ERE outcome, when it arrives, either:

* Confirms the provisional cluster identifier (singleton outcome), or
* Replaces it with a different cluster identifier.

ERS shall accept, persist, and expose the latest cluster assignment returned by ERE, even if this replaces a previously issued provisional identifier.

ERS shall not return a timeout error for a single-mention request: when the execution window expires, it returns the provisional identifier.
A bulk request that exceeds its bulk budget fails as a whole with a timeout error, and no partial result is returned.

A canonical identifier is therefore always returned for each accepted resolution request, unless the request itself is invalid, a backing service is unavailable, or a bulk request exceeds its bulk budget.

Provisional identifiers are valid canonical placements until replaced by a subsequent ERE outcome.

*Provisional-only mode.* When the single-mention budget is set to zero, ERS does not contact the ERE at all and returns a provisional identifier immediately.
No ERE outcome ever confirms or replaces these identifiers.
This mode is intended only for deployments without an ERE.

== Scope and Applicability

This decision applies to all ERS client-facing resolution APIs.

It governs client-visible timeout behaviour and the lifecycle of provisional placements.

It does not prescribe specific timeout durations, infrastructure mechanisms, or messaging technologies; the configured budgets are listed in xref:Installation/environment-variables.adoc#ers-api[Environment Variables].

== Considered Options

* Return explicit error on engine timeout and never issue provisional identifiers.
* Expose asynchronous polling or pending states to clients.
* Issue provisional singleton placements within bounded time and allow later correction by ERE. _(Selected)_

== Rationale

Issuing provisional singleton placements ensures that clients receive a usable canonical identifier within bounded time, independent of engine latency.

Returning a provisional identifier when the execution window expires prevents engine delay from causing client-visible failure.

Deriving the provisional identifier with the same rule as an ERE singleton makes a separate recommendation message unnecessary and keeps clustering authority exclusively in the ERE.

Allowing later correction by ERE preserves a single authoritative clustering model while maintaining operational continuity for clients.

== Consequences

* Clients always receive a canonical identifier for accepted single-mention requests within the time budget; bulk requests either complete within the bulk budget or fail as a whole.
* Canonical identifiers previously returned to clients may change if the ERE subsequently returns a different clustering outcome.
* Provisional singleton clusters may exist temporarily and may later be merged or replaced by ERE.
* Clients must rely on refreshBulk or lookup mechanisms to observe placement changes over time.
* Resolution latency variability does not translate into client-visible errors for single-mention requests.
