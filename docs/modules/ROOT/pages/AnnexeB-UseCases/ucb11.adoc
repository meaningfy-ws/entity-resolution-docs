= UC-B1.1: Resolve via ERS API

*Use Case Level:* Blue (User-goal) +
*Primary Actor:* Originator (e.g. TED-SWS, Link Curation Backend, or any submitting system) +
*Supporting Actors:* Request Registry (append-only store for request registration and idempotency); Decision Store (latest Cluster Assignment per mention); Messaging Middleware (asynchronous interaction with the Entity Resolution Engine); Entity Resolution Engine (ERE) +
*Scope:* Entity Resolution System (ERSys) — Public API (ERS)

This Blue use case refines xref:AnnexeB-UseCases/ucw1.adoc#uc-w1[UC-W1: Resolve Entity Mention]. The shared contract — canonical identity definition, the two time budgets, the Provisional Identifier issuance rule, the success and minimal guarantees, and the main and alternate scenarios — is stated in UC-W1 and is not restated here. This page states only the realisation specifics of the synchronous ERS API path.

== Stakeholders and Interests

* The Originator requires a canonical identifier for each submitted Entity Mention within the time budget of the request.
* ERS operators require deterministic timeout handling, strict idempotency enforcement, and isolation between synchronous API guarantees and asynchronous engine processing.
* Downstream consumers rely on cluster identifiers as canonical identity references and must reconcile later Cluster Assignment changes via refresh mechanisms.

== Brief Description

This use case describes the synchronous processing performed by ERS when an Originator submits a request to resolve one Entity Mention, realising the contract of xref:AnnexeB-UseCases/ucw1.adoc#uc-w1[UC-W1] over the public ERS API.

Upon receiving a valid request, ERS:

* registers the request in the Request Registry and enforces idempotency,
* forwards the mention to ERE using the resolve interaction,
* waits for an ERE response within the ERS–ERE execution window.

If ERE responds within the execution window, ERS returns the cluster identifier produced by ERE and records the resulting Cluster Assignment (along with alternatives) in the Decision Store. If ERE does not respond within the execution window, ERS deterministically derives a singleton cluster identifier (Provisional Identifier) and returns it to the Originator (HTTP 202, marked PROVISIONAL); an ERE answer within the window is returned with HTTP 200, marked CANONICAL. ERS sends no further message to ERE; the outcome of the original request, as defined in the xref:ERS-ERE-Contract/interface.adoc[ERS–ERE contract], later confirms or replaces the Cluster Assignment.

Bulk submission is treated as a finite list of independent single-mention requests. The mentions are resolved concurrently, each within the execution window, and the whole request is bounded by the bulk budget. If the bulk budget is exceeded, the whole request fails with a timeout error (HTTP 504, SERVICE_TIMEOUT) and no partial result is returned; Provisional Identifiers already issued remain stored. A bulk response is HTTP 200 when all mentions are canonical, HTTP 202 when all are provisional, and HTTP 207 when they are mixed or any mention failed; each failed mention carries the same error code as a single request would.

== Preconditions

* The request contains the required entity mention identifiers `(source_id, request_id, entity_type)`, the entity representation payload, and the declared payload format.
* The request may include an optional opaque context object (e.g. notice identifier). Context is treated as correlation metadata and does not influence clustering outcomes.
* ERS maintains a Request Registry and a Decision Store.

== Trigger

The Originator submits a resolve request containing one Entity Mention.

== Success Guarantee (Postconditions)

The success and minimal guarantees, and the main and alternate scenarios, are those of xref:AnnexeB-UseCases/ucw1.adoc#uc-w1[UC-W1] and are not restated here. This Blue path adds only the following realisation specifics:

. The request is registered in the Request Registry and correlated using `(source_id, request_id, entity_type)`.
. Idempotency is enforced at registration: an identical repeated submission returns the mention's current Cluster Assignment from the Decision Store (HTTP 200, marked CANONICAL) without contacting ERE, per the idempotency rules stated in xref:AnnexeB-UseCases/ucw1.adoc#uc-w1[UC-W1] (including the idempotency-conflict rule).

== Minimal Guarantees (On Failure)

As stated in xref:AnnexeB-UseCases/ucw1.adoc#uc-w1[UC-W1]. No additional Blue-specific minimal guarantees apply.

== Extensions

These extensions are realisation-specific deltas over the UC-W1 contract:

1a. Invalid or malformed request — ERS rejects the request and returns a validation error (HTTP 400, VALIDATION_ERROR). +
1b. Unsupported entity type or payload format, or mention content that cannot be parsed or exceeds the configured maximum size — ERS returns an explicit error (HTTP 400, PARSING_FAILED). +
2a. Idempotency conflict — realisation of the UC-W1 idempotency-conflict rule: if the same `(source_id, request_id, entity_type)` is submitted with a different payload, ERS returns an IDEMPOTENCY_CONFLICT error (HTTP 422) and does not modify the Decision Store. +
2b. Backing service unavailable — if the document store, Redis or the messaging channel is unavailable, ERS returns a SERVICE_UNAVAILABLE error (HTTP 503); no Provisional Identifier is issued. +
3a. Rate limit exceeded — ERS does not implement rate limiting; where it is required, a gateway in front of the ERS API enforces it and rejects the request.

== Special Requirements

* Singular semantics: each request processes exactly one Entity Mention.
* Cluster identifiers are canonical identifiers and originate either from ERE clustering or deterministic singleton derivation.
* ERE decisions are binding; ERS does not override clustering outcomes.
* ERS stores only the latest Cluster Assignment per mention in the Decision Store and does not maintain canonical entity lineage.
* Late or duplicate ERE responses update the Decision Store only if applicable under correlation rules.

== Technology and Data Variations

Supported payload formats and entity types are configuration-driven. Resolution interaction types and message formats are defined in the ERS–ERE contract.

== Frequency of Occurrence

High; expected to be invoked repeatedly by ingestion and integration pipelines.
