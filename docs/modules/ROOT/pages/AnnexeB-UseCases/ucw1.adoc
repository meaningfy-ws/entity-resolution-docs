= UC-W1: Resolve Entity Mention

*Use Case Level:* White (Summary) +
*Primary Actor:* Originator (e.g. TED-SWS, Link Curation Backend, or any submitting system) +
*Scope:* Entity Resolution System (ERSys)

== Stakeholders and Interests

* The Originator requires a canonical identifier for each submitted Entity Mention and expects the identifier to be returned within the time budget of the request.
* Downstream consumers depend on cluster identifiers as canonical identity references and must be able to reconcile changes in Cluster Assignment over time.
* ERS operators require predictable timeout handling, strict idempotency, and clear separation between client-facing guarantees and engine-internal processing.

== Brief Description

The Originator submits an Entity Mention to ERSys in order to obtain the canonical identifier under which the mention is currently clustered.

Canonical identity is defined as a cluster managed by the Entity Resolution Engine (ERE). Cluster identifiers are canonical identifiers. ERE is authoritative for clustering outcomes and its decisions are binding.

A single time budget applies to a single-mention request: it is both the ERS–ERE execution window and the bound on the ERS response.
The Originator's own timeout must be longer than this budget.
For a bulk request, each mention is resolved concurrently within the execution window, and the whole request is bounded by a separate bulk budget.

Upon receiving a valid request, ERS forwards the mention to ERE for clustering and waits within the ERS–ERE execution window.

If ERE responds within the execution window, ERS returns the cluster identifier provided by ERE and records the corresponding Cluster Assignment in the Decision Store.

If ERE does not respond within the execution window, ERS:

* deterministically derives a singleton cluster identifier (Provisional Identifier), using the same rule the ERE uses for a new singleton cluster,
* returns this Provisional Identifier to the Originator.

ERS sends no further message to ERE: ERE keeps processing the original request. When its outcome arrives, a singleton outcome confirms the Provisional Identifier and any other outcome replaces it. ERS records and exposes the latest Cluster Assignment received from ERE in the Decision Store.

When the single-mention budget is set to zero (provisional-only mode, for deployments without an ERE), ERS does not contact ERE and returns a Provisional Identifier immediately; such identifiers are never confirmed or replaced.

Cluster Assignment for a mention may change over time. Stability means that cluster identifiers are not reused improperly; it does not imply immutability of assignment.

Follow-up retrieval of updated Cluster Assignments is performed through the dedicated refresh operation defined separately.

== Preconditions

* The request includes required correlation information: `source_id`, `request_id`, and `entity_type`.
* The Entity Mention payload conforms to supported formats and configured entity types.

== Success Guarantee (Postconditions)

For every valid request:

. ERS registers the request and enforces idempotency based on correlation identifiers.
. ERS forwards the mention to ERE for clustering, unless provisional-only mode is configured.
. ERS returns a canonical identifier within the time budget, either:
.. the cluster identifier returned by ERE, or
.. a deterministically derived Provisional Identifier.
. The returned identifier is a valid canonical identifier at the time of response (at-response guarantee).
. ERS records the latest Cluster Assignment per mention in the Decision Store; where a Provisional Identifier was returned, ERE subsequently confirms or replaces the assignment and ERS records the latest authoritative Cluster Assignment, observable via the refresh operation (eventual-consistency guarantee).

== Minimal Guarantees (On Failure)

. If the request is syntactically invalid or violates mandatory validation rules, ERS returns an explicit validation error.
. If a critical dependency (for example the Decision Store or the messaging channel) is unavailable, ERS returns an explicit service-unavailable error; no Provisional Identifier is issued in that case.
. Expiry of the ERS–ERE execution window alone does not result in an error for a single-mention request; instead, a Provisional Identifier is issued.
. A bulk request that exceeds its bulk budget fails as a whole with a timeout error, and no partial result is returned; Provisional Identifiers already issued for some of its mentions remain stored.

== Main Success Scenario

Direct Engine Response:

. The Originator submits a resolve request containing a single Entity Mention and required identifiers.
. ERS validates and registers the request.
. ERS forwards the mention to ERE.
. ERE returns a cluster identifier within the execution window.
. ERS returns that cluster identifier to the Originator and records the Cluster Assignment in the Decision Store.

== Alternate Scenarios

Provisional Identifier Issuance:

. The Originator submits a resolve request.
. ERS validates and registers the request.
. ERS forwards the mention to ERE.
. ERE does not respond within the ERS–ERE execution window.
. ERS derives a deterministic Provisional Identifier and returns it to the Originator.
. ERE completes the original request; its outcome later confirms or replaces the Cluster Assignment.
. ERS updates the Decision Store to reflect the latest Cluster Assignment.

== Extensions

1a. Invalid or malformed request — ERS rejects the request and returns a validation error. +
1b. Unsupported entity type or payload format, or mention content that cannot be parsed or exceeds the configured maximum size — ERS returns an explicit error indicating the unsupported type or format. +
2a. Repeated request (idempotent replay) — If the same `(source_id, request_id, entity_type)` is submitted again with identical payload, ERS returns the mention's current Cluster Assignment from the Decision Store as a canonical identifier, without contacting ERE. This may differ from the first answer if ERE or a Curator changed the assignment since. If no Cluster Assignment exists yet, ERS forwards the request to ERE again. +
2b. Idempotency conflict — If the same `(source_id, request_id, entity_type)` is submitted with a different payload, ERS returns an idempotency-conflict error and does not modify the Decision Store.

== Special Requirements

* The resolve operation is idempotent with respect to request registration: a replay creates no new request and returns the current Cluster Assignment.
* Cluster identifiers are canonical identifiers and originate either from ERE clustering or deterministic singleton derivation.
* ERE decisions are binding; ERS does not override clustering outcomes.
* ERS stores only the latest Cluster Assignment per mention in the Decision Store; canonical entity lineage is not maintained.

== Technology and Data Variations

Entity Mention payloads may vary in format and structure, subject to validation rules and supported entity type configuration.

== Frequency of Occurrence

High; expected to be invoked repeatedly as part of automated ingestion, reconciliation, and synchronisation pipelines.
