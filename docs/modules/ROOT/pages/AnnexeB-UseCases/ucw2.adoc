= UC-W2: Recommend Resolution Update (Curation)

*Use Case Level:* White (Summary) +
*Primary Actor:* Curator (human user) +
*Scope:* Entity Resolution System (ERSys)

// Body previously used the generic "User"; aligned to the glossary preferred term "Curator" (same actor — the Blue children UC-B2.1/UC-B2.2 were already actor-aligned).

== Stakeholders and Interests

* The Curator requires a controlled mechanism to request re-evaluation of a mention's current Cluster Assignment when the observed canonical identity appears incorrect or incomplete.
* Originators and downstream consumers require that any change in canonical identity remains consistent with the engine-authoritative model and is observable through standard synchronisation mechanisms.
* ERS operators require that user actions do not introduce independent governance semantics or override engine authority.

== Brief Description

This use case describes how a Curator requests re-evaluation of the Cluster Assignment of an existing Entity Mention.

Canonical identity is defined as a cluster managed by the Entity Resolution Engine (ERE). Cluster identifiers are canonical identifiers. ERE is authoritative for clustering outcomes and its decisions are binding.

A Curator may request re-evaluation in one of two forms:

. *Placement Recommendation* — the Curator recommends that a mention be assigned to a specific cluster: either its current cluster (Accept) or one of the candidate clusters stored with its latest ERE outcome (Assign).
. *Exclusion Recommendation* — the Curator recommends that the current cluster and all stored candidate clusters be excluded from consideration during re-resolution (Reject).

A Curator cannot recommend an arbitrary target cluster or a partial exclusion list.

Curator actions are recommendations only. They do not directly modify the Cluster Assignment stored in ERS.

Upon receiving a valid re-evaluation request, ERS records the Curator action and forwards the recommendation to ERE as a resolution request carrying the proposed or excluded cluster identifiers. ERE evaluates the request according to its internal clustering logic and returns an authoritative clustering outcome. Honouring a recommendation is optional for an ERE: it may treat recommendations as advisory. The Basic ERE ignores them and answers a request for an already-resolved mention from its stored state, so with the Basic ERE Curator actions do not change placements.

ERS records the latest Cluster Assignment returned by ERE in the Decision Store and exposes it as the current canonical identity.

A re-evaluation request may result in:

* confirmation of the existing Cluster Assignment,
* assignment to a different existing cluster, or
* assignment to a new cluster created by ERE.

Cluster Assignment may change over time as a result of such re-evaluation. Stability means that cluster identifiers are not reused improperly; it does not imply immutability of assignment.

== Preconditions

* The mention exists in the Decision Store with a current Cluster Assignment.
* The Curator provides the required mention identifiers and, for a placement to another cluster, one of the stored candidate cluster identifiers.

== Trigger

The Curator selects an existing mention (or a set of mentions) and submits a recommendation to re-evaluate its current Cluster Assignment.

== Success Guarantee (Postconditions)

For a valid re-evaluation request:

. ERS records the Curator action and forwards the recommendation to ERE without altering the current Cluster Assignment.
. ERE evaluates the recommendation and determines the authoritative clustering outcome.
. ERS updates the Decision Store to reflect the latest Cluster Assignment returned by ERE.
. Any change in Cluster Assignment updates delta tracking to support refresh operations.

The resulting Cluster Assignment is authoritative and replaces the previous assignment if different.

== Minimal Guarantees (On Failure)

* If the re-evaluation request is invalid or refers to an unknown mention, ERS returns an explicit error.
* A placement to a cluster that is not one of the stored candidates is rejected (conflict).
* Forwarding to ERE is best-effort: the Curator action is recorded first; if ERS cannot publish the request, the failure is only logged, the Curator sees the action as accepted, and the existing Cluster Assignment remains unchanged.
* Curator recommendations do not directly modify canonical identity without an authoritative outcome from ERE.

== Main Success Scenario

Placement Recommendation:

. The Curator requests that a mention be assigned to its current cluster or to one of its stored candidate clusters.
. ERS validates the request and forwards it to ERE as a placement recommendation.
. ERE evaluates the recommendation and determines the resulting Cluster Assignment.
. ERS records the returned Cluster Assignment in the Decision Store.

== Alternate Scenarios

Exclusion Recommendation:

. The Curator requests re-resolution with the current cluster and all stored candidate clusters excluded.
. ERS forwards the exclusion list to ERE.
. ERE re-evaluates clustering under its internal logic.
. ERS records the authoritative Cluster Assignment returned by ERE.

== Special Requirements

* Curator actions are recommendations and do not constitute governance overrides.
* ERE decisions are binding.
* ERS stores only the latest Cluster Assignment per mention and does not maintain canonical lineage.
* All Cluster Assignment changes resulting from re-evaluation must update delta tracking.
* One action per placement: after one Curator action on a mention's current placement, further Curator actions on that mention are rejected as already curated until ERE returns a changed outcome for it. This guard applies to Curator actions only; it does not lock the Cluster Assignment, and ERE authority is unaffected.

== Technology and Data Variations

The re-evaluation interface may be exposed through different transport mechanisms depending on deployment. Interaction types and message structures are defined in the xref:ERS-ERE-Contract/interface.adoc[ERS–ERE contract].

== Frequency of Occurrence

Low to medium; invoked when manual intervention or operational correction is required.
